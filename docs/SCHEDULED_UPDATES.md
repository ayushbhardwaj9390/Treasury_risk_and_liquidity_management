# Scheduled collection readiness

This release stores requested update intervals for registered connectors in a dedicated company database. GET/PUT `/api/v1/scheduled-updates` require an active identity; only GROUP_TREASURER can save settings. Writes use an expected version, reject unknown fields and out-of-range intervals, and produce audit records. Registration must exist, and inactive connectors cannot be enabled. Saving settings never promotes source authority or sends a payment or hedge trade.

The browser component uses GET/PUT `/api/scheduled-updates` through the authenticated company proxy. Recorded demo mode has a separate fictional, visit-only example: there is no real background timer or collected data. This panel is separate from the five-second synthetic walkthrough.

`python scripts/run_scheduled_updates.py --actor <provisioned-operator>` runs one bounded readiness pass (maximum 100 due jobs). It records BLOCKED attempts, advances the next requested check, and increments a conditional revision so overlapping passes cannot claim the same revision. Paused jobs are skipped. It does not start a daemon or install an operating-system schedule. The command is an operator tool: its actor argument is not an authentication substitute for internet-facing APIs; only trusted deployment operators should access the database/runtime.

**External collection remains blocked.** No credential-backed collection adapter or distributed worker is configured in this release. The CLI deliberately has no arbitrary URLs, imported adapter names, shell execution or success-recording API. A future deployed worker must use the registered, independently approved adapters, existing resilient runner, canonical ingestion, checkpoint idempotency, quarantine, certification/SLA/parallel-run gates and human source promotion. SHADOW records must remain shadow; ACTIVE permission is never inferred from a schedule. Deployment scheduling, workload identity, secrets management, monitoring and operational approval are required before claiming unattended updates.

Freshness uses the registered connector's accepted-event checkpoint, **not** the connector table's default `last_success_at` timestamp. Missing accepted evidence is MISSING; old events are STALE; future timestamps require review. RECENT means only that an accepted event was recently recorded for that connector, not complete account coverage, domain-specific quality or certification. The panel states this limitation. A blocked attempt never changes accepted checkpoint evidence or makes stale data appear fresh.

Migration: `0029_scheduled_updates`, following `0028_company_preferences`. Checks cover role restrictions, unknown/inactive connectors, strict interval limits, optimistic conflicts, missing/stale/future evidence, repeated due attempts, audit records and unchanged SHADOW authority. Frontend tests ensure bounded intervals and explicitly fictional missing-data examples.
